# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Uses LLMs to annotate business process descriptions from the PET dataset with process element mentions (Activity, Actor, Activity Data, XOR/AND Gateway, Condition/Further Specification) and the relations between them (flow, uses, actor performer/recipient, same gateway, further specification), then scores predictions against the gold annotations in `res/gold/pet.jsonl` (45 documents). Mention detection also runs on Quishpi and MedicalProcessInstruks, uq-pet-token's other datasets (see Evaluation). The results are reported in a paper, so runs log everything needed to describe them.

## Commands

Environment is managed with uv (Python ≥3.10, `package = false` — nothing is built or installed; scripts run directly from `src/`, so `src/` is the import root for `autoannotate`, `eval`, `experiments`, `data`).

```bash
uv sync
uv run marimo edit notebooks/run_experiments.py   # edit/preview/run configs, live scores, export, data checks
uv run python notebooks/run_experiments.py --config configs/pet/md.yaml --workers 4   # the same headless
uv run python notebooks/run_experiments.py --config configs/pet/md.yaml --only 'gemma-4-31b-*'   # some of them
uv run python notebooks/run_experiments.py --export   # test-predictions.jsonl for uq-pet-token, per run
uv run python notebooks/run_experiments.py --check    # same data and scoring as uq-pet-token's results?
uv run marimo edit notebooks/eval_table.py   # results table: scores every pet.jsonl in res/pred/
uv run --project .. python scripts/uq-pet-token-splits.py  # gold files, in uq-pet-token's environment
uv run marimo check notebooks/   # lint the notebooks
uv run pytest                       # all tests
uv run pytest tests/test_mentions.py -k repeated   # a subset
uv run ruff check src/ tests/      # lint; add --fix for the auto-fixable ones
```

Tests in `tests/` never call an LLM: `conftest.py` provides `make_doc` (builds a `Document` from whitespace-tokenized sentences) and `fake_client` (stands in for `openai.OpenAI`; the answer can be a function of the request, which may raise). Known bugs are kept as `xfail(strict=True)` tests, so fixing one makes its test fail until the marker is removed. Ruff is configured in `pyproject.toml` (Google docstring convention, 100 columns, missing docstrings allowed, no docstring rules in `tests/`); the code does not pass it cleanly yet.

API keys come from `.env` (`OPENAI_API_KEY`, `NHR_API_KEY`; see `.env.template`).

Source files mix CRLF and LF line endings; keep each file's existing endings when editing.

## Experiments

A config file is a YAML file (`*.yaml`/`*.yml`) in `configs/` or a subfolder like `configs/pet/`; `experiments.config.load_configs` turns it into run configs. With `model` it is one config named after the file stem; with `models` (entries `name`, `model`, `reasoning_effort` scalar or list) one config per model and effort, named by `config.run_name` (`[<dataset>-]<name>-<task>[-reasoning-<effort>]`, no suffix for `none`), so existing `res/pred/` folders keep their names. `configs/<dataset>/<task>.yaml` hold the mention experiments (keys: `dataset` (`pet` default, `quishpi`, `medical`), `task` (`end-to-end`, `md` = mentions only, or `md-test-sentences`; non-PET datasets only the `md` ones), `provider`, `model`, `reasoning_effort`, `max_documents`, `repeats`; see `configs/README.md`, which also records which `reasoning_effort` values each NHR model accepts). `notebooks/run_experiments.py` runs them (in the editor, or as a script with `--config`, `--only`, `--workers`, read with `mo.cli_args()`; it is not called `experiments.py`, as running it as a script puts `notebooks/` first on `sys.path`). The config file's text is edited in the notebook and parsed with `config.parse_configs` (`load_configs` reads a file with it). `experiments.batch` does the work: `problems` (duplicate names, missing gold files) and `clients` (API keys) before the first call, then `run_config` per config and repeat: `runner.annotate_run` → `report.score_run` → `test_split.export`; a failing run skips the rest of its config. Finally `report.write_summary` rebuilds `res/pred/runs.csv` and `res/pred/summary.csv` from **every** run folder on disk. `annotate_run(on_document=...)` is called in the calling thread after each saved document, which the notebook uses to show `report.scores_so_far` (the scores of the documents done, and of the test sentences among them) while a run goes on; `runner.read_predictions`/`read_calls` take the write lock. `runner.build_annotators(config, client)` builds a run's annotators; the prompt preview calls it with `client=None`, so it shows what a run sends, and `runner.resume_problem` says why an existing run would refuse to resume. The run cell must not depend on cells that re-run when it bumps the `mo.state` that refreshes the run table, or it runs again.

Run folder `res/pred/<config>/run-<i>/`: `<task>/pet.jsonl` (predictions), `calls.jsonl` (one line per LLM call: tokens, duration, finish reason, raw response, reasoning, parser issues), `run.json` (settings, rendered prompts, a session per start with git commit/dirty flag, package versions, gold sha256, plus totals), `metrics.json`. Documents are annotated by a thread pool (`--workers`); `_write_lock` guards the shared files, and `BaseAnnotator.annotate` creates a parser per call so issues don't mix between threads. Transient API errors (`runner.TRANSIENT_ERRORS`) skip the document (session outcome `incomplete`); other errors or `MAX_CONSECUTIVE_FAILURES` in a row stop the run. Resuming skips documents already in `pet.jsonl` (the predictions file has that name for every dataset) but raises if `RunConfig.settings()` (dataset, task, provider, model, reasoning effort) or the rendered prompts differ from `run.json`; a `run.json` without `dataset` is PET (`runner.manifest_settings`). `totals` counts only the latest successful call per (document, step) of completed documents; the rest are `discarded_calls`.

All prompt text lives in `prompts/` (see `prompts/README.md`): the instruction templates `mentions.txt`/`relations.txt`, structured after Neuberger et al. (ER 2024) as Context / Task Description / Restrictions (`{{type_definitions}}`, `{{procedure}}`, `{{disambiguation}}`, `{{example}}`), and per dataset `prompts/<dataset>.yaml` with type descriptions (YAML `>-` paragraphs, order = prompt order), the step-by-step procedure, disambiguation hints and the format example template (`|-`). `src/experiments/definitions.py` only loads them (`mention_prompt(dataset)`, `relation_prompt(dataset)` (PET only) return the definitions and the other template values, `TEMPLATE_VALUES`, which the annotators take as `template_values`; files are read on every call, `PROMPT_DIR` can be monkeypatched in tests). `tests/test_prompts.py` checks that type names match the dataset's tags, that every example parses, and that every dataset fills the whole template. PET's and Quishpi's descriptions are hand-written; MedicalProcessInstruks has unnamed types (`T03`…`T43`, named by begin tag id like uq-pet-token), so each is described by its most frequent texts in the training sentences (`Dataset.train()`, everything but the test split); the wording and settings of that generation are in `prompts/medical.yaml`. Every format example shows uq-pet-token's 5 bootstrap sentences (`Dataset.bootstrap()`, `res/gold/<dataset>-bootstrap.jsonl`, the labelled sentences its token classifiers start from) as one numbered input with their gold mentions (`definitions.mention_example` fills the YAML's `{{sentences}}`/`{{mentions}}`); PET's relation example is the same sentences with the mentions and relations from `pet.jsonl` (`relation_example_document`, relations to other sentences dropped). Runs from before the examples came from the bootstrap sentences can't be resumed either. The descriptions' whitespace was cleaned when they moved out of Python, so runs from before that commit can't be resumed (their `run.json` prompts differ).

## Pipeline architecture

Two LLM calls per document, end to end:

1. **Mentions** — `LLMMentionAnnotator` sends the document as numbered sentences (`i: tok tok tok`) and asks for `text<TAB>type<TAB>sentence_id` lines. `MentionParser` maps those back to token indices using LangExtract's `WordAligner` per sentence (exact match first, fuzzy fallback; a fuzzy match may not reuse tokens already claimed by an exact match).
2. **Relations** — `LLMRelationsAnnotator` sends the text with predicted mentions inlined as XML-ish tags carrying their list index (`<actor id=1> clerk </actor>`, via `util.format_document_text_with_entity_mentions`) and asks for `type<TAB>head_id<TAB>tail_id` lines. `RelationParser` turns these into `Relation`s that reference mentions **by index into `document.mentions`** — so mention order/removal matters (`Document.remove_mention` reindexes relations).

Parsers never raise on bad LLM output: they skip the line and call `BaseParser.report(kind, message)`, which prints and records it. Kinds are prefixed `dropped_` (line not used), `placed_` (used after fuzzy/out-of-order alignment) or are `ignored_line` (no tab, e.g. chatter); `runs.csv` sums the `dropped_` ones. `BaseAnnotator.annotate` returns an `LLMAnnotation` with the parsed doc plus everything the run log needs (tokens incl. `reasoning_tokens` when reported, raw response, `reasoning_content`/`reasoning` from the message's extra fields, finish reason, duration, issues).

Shared plumbing in `src/autoannotate/`:
- `base.BaseAnnotator`: builds chat-completion params; prompts are authored with a `developer` role and rewritten to the provider's `instruction_role` (`system` for NHR/vLLM-served open-weight models). `reasoning_effort=None` omits the parameter. `get_instruction()` on the mention/relation annotators returns the document-independent instruction prompt.
- `providers.py`: `PROVIDERS` registry; NHR@FAU is an OpenAI-compatible gateway (LiteLLM), so everything goes through the `openai` client. The gateway caches responses to identical requests, so `Provider.extra_body` sends `{"cache": {"no-cache": True}}` with every NHR request; without it, repeated runs are copies of the first.
- `prompts.Prompt`: a template file (or `text=`) with `{{param}}` placeholders; missing or unknown params assert. The mention and relation annotators take their template path (`template=`); only the unused entities template is still in `resources/prompts/`.
- `data.py`: `Document`/`Token`/`Mention`/`Relation`/`Entity` plus JSONL import/export. The importer lowercases mention and relation types, so gold `"Activity Data"` and predicted types compare as `"activity data"`.
- `entities.py` (`LLMEntitiesAnnotator`, coreference into entities) and `BaseAnnotator.batch_line` exist but are not used by the current pipeline.

## Evaluation

All matching lives in `src/eval/scoring.py`, used by both the experiment reports and the results notebook. Matching is lenient: a predicted mention matches a gold one if types are equal and token sets **overlap at all**; a relation matches if type is equal and both head and tail mentions overlap. Matching is greedy one-to-one per document. With `exact=True` (`mention_stats`, `relation_stats`, `score`) mentions, and relation heads and tails, must cover the same tokens instead; the results notebook scores both ways and has a toggle, while `metrics.json` is always the lenient score. `scoring.summarize` reports macro (mean ± population std of per-document P/R/F1), micro (summed counts) and per-type micro scores. A document with no gold and no predicted annotations scores 1.0 (`eval.metrics.Stats`). `summary.csv` uses the sample SD across runs.

`notebooks/eval_table.py` scores every `res/pred/<folder>/run-<i>/<task>/pet.jsonl` (config runs) and `res/pred/<folder>/<task>/pet.jsonl` (predictions from before the configs) with `scoring.score` rather than reading `metrics.json`; the folder name says what to score: `end-to-end` (`md` and `re`), `md`, or `re`/`isolated-re`; `run.json` says the dataset, and a dropdown picks which dataset's runs to show. Notebook cells must not define the same name twice, so cell-local variables start with `_` (`uv run marimo check` catches it).

This project is a baseline for uq-pet-token, the repository root (`..`; this project is its `llm-annotation-eval/` folder, with its own uv environment), which trains token classifiers on PET v1.1 and evaluates on a fixed 84-sentence test split. `src/eval/datasets.py` lists the datasets (`DATASETS`: mention types as the BIO tags spell them, sentence file, test file, bootstrap file, and for PET the document file). uq-pet-token splits Quishpi (201 sentences, 41 test) and MedicalProcessInstruks (325, 65) like PET; `scripts/uq-pet-token-splits.py` writes `res/gold/<dataset>.jsonl`, `res/gold/<dataset>-test.jsonl` and `res/gold/<dataset>-bootstrap.jsonl` (PET's named `pet-v1.1*`) with uq-pet-token's own `data_prep` (run in its environment) and checks PET's sentences and test split are unchanged; with `--check` it only compares all nine files. `experiments.checks.run` can run that check (optional, slow) and also compares the test gold stored in uq-pet-token's reported supervised runs (`predictions.npz`) with `res/gold/`, rescores their predictions against their `results.csv`, checks every run's recorded gold sha256 and that no test sentence of 5+ words is in a prompt; it returns a `Report` the notebook shows. The medical dataset is gated, so its files are gitignored and tests on them skip when missing. Whole-document runs on those datasets annotate their sentences grouped back into documents (`datasets.documents_from_sentences`, mentions from the BIO tags); `datasets.read_documents` reads either format, so `gold_file` arguments take both. `src/eval/test_split.py` reproduces that evaluation: `res/gold/pet-v1.1-test.jsonl` is the split (generated with uq-pet-token's `load_pet_splits`, same format and order; PET v1.1 labels differ from `res/gold/pet.jsonl` in 8 test sentences), predicted mentions of test sentences become BIO tags with the dataset's `types` passed in (overlaps: first listed wins; unknown types kept so they count as wrong), and `evaluate` mirrors uq-pet-token's `evaluate_predictions` with seqeval 1.2.2 (strict span match, micro). `export` writes `test-predictions.jsonl` next to a run's `pet.jsonl`; `batch.run_config` calls it after scoring each run, and `report.export_test_predictions` for every run. Task `md-test-sentences` annotates each test sentence on its own: `runner.input_documents` turns the test split into one-sentence documents with ids `<document>#<sentence-ID>` (`test_split.sentence_documents`), `batch.run_config` passes the test file as the run's input, and `report.score_run` scores those runs only on the test split. `metrics.json` of every run that covers the test sentences has a `test` entry, which `runs.csv`/`summary.csv` show as `test_*` columns. `evaluate` also returns uq-pet-token's partial-match scores (`entity_partial_*`, same type and a shared token, each gold mention once). Verified identical to uq-pet-token's own `evaluate_predictions` (all 8 metrics) on real predictions. The notebook's "Comparison with uq-pet-token" table reads uq-pet-token's supervised baseline from `../results/supervised/<sweep>/` (`run_config.json` for dataset and checkpoint, `summary.json` for the complete `test/pool_100pct` run, its `results.csv` with one row per model seed) and lists it above the LLM runs' test-split scores, exact or partial match.

`src/data/pet.py` is an older parallel copy of the data model (`PetDocument`, etc.); only `src/eval/metrics.py` imports it. Everything else uses `autoannotate.data`.
